## Engines

Vibezeo detects these coding agent CLIs on your login shell's `PATH` and shows how to install the missing ones. Each runs on your own subscription and signs in by itself. This table is generated from the app's engine registry.

Antigravity CLI runs in terminal panes only, as Google ships it. Kiro CLI runs in terminal panes and, through its Agent Client Protocol mode, in Thread mode. ## Any ACP agent in Thread mode

Agents that speak the Agent Client Protocol (ACP) can run threads. Cursor Agent, Gemini CLI, Grok, Kiro CLI and OpenCode do out of the box. Gemini CLI runs as `gemini --acp`, or `gemini --experimental-acp` on older releases. To add another, open **Settings › Engines › ACP agents** and choose **Add an ACP agent…**:

- **Name**, **Command** (a command on your `PATH`, or its full path), **Arguments** and **Environment variables**. **Goose** fills in `goose acp`.
- **Test** starts the command, asks it to introduce itself, waits up to 10 seconds and stops it. You see its name, version and how it signs in. If it doesn't answer as an ACP agent, it says "Not an ACP agent" and why, and nothing is saved. **Add** runs the same test before saving.
- The agent then appears in the Thread engine picker as "via ACP". Threads run the command at the path saved when you added it, never another program of the same name. Agents you add run on this computer only, not in SSH or WSL folders, and only in Thread mode.
- **Remove** stops the agent's threads. They stay readable but won't run again: an agent you add later, even with the same name, is a new engine.
- The agent signs in its own way. Vibezeo never sees or keeps its keys: a variable whose value looks like a key or token is refused, and so are variables that change which home an engine uses or what a program loads. When it asks for a sign-in, the thread names the methods it offers: sign in with the agent's own command in a terminal, then try again.

Vibezeo shows what each agent reports over ACP: messages, tool calls, approvals and models. Usage and status beyond that depend on the agent. When an agent asks for approval without offering a one-time allow, **Allow once** declines the request rather than allowing it for good.

## Local models

If you run models on your own computer with Ollama or LM Studio, Codex can use one of them: its prompts, and the code they carry, then go only to that server at `127.0.0.1`. Open **Settings › Engines › Local models**:

- Vibezeo asks `127.0.0.1` for model servers when you open the page or choose **Check again**: Ollama at port 11434, LM Studio at 1234 and llama.cpp's `llama-server` at 8080. It never asks another computer, and never on a timer. **Add a port…** adds another port on this computer.
- Each running server lists its models with the size and parameter count the server reports. Vibezeo doesn't download or install anything, and doesn't vouch for how well a model handles an agent's tools.
- **Start in Codex** opens a Codex pane in the open local folder. Codex runs in a provider home of its own for that server and model, under `providers/codex/`, whose `config.toml` points it at `http://127.0.0.1:<port>/v1` and turns off its update check. Your own `~/.codex` and your Codex accounts aren't touched, and no sign-in is needed. The pane says **On this computer**.
- Every start of that pane, including Restart and after you reopen Vibezeo, runs the same way: never on your Codex account, an OpenAI key or an access token in your environment, never on a remote exec server, and with no proxy. The model and server are also set on Codex's command line, after its other arguments, where they sit above every Codex configuration file but an administrator's. Codex's `/review` and memories use the same model. Its sub-agents are off, since a sub-agent can choose its own model, and approval requests come to you, never to a reviewing sub-agent. Codex's hosted connectors, its plugins (it would otherwise fetch their catalog from GitHub when it starts), its usage metrics and its update check are off too. Of your Codex arguments in Settings › Engines, only the sandbox, approval and reasoning ones apply.
- A local pane uses none of the repository's own Codex settings: its `.codex/config.toml`, hooks and MCP servers. At every start Vibezeo marks the pane's folder, each folder above it and, for a worktree, its main checkout as untrusted, both on Codex's command line and in the pane's home, and starts Codex in that folder. Codex then loads none of their settings, and never asks to trust the folder (newer versions say it opens restricted, which changes nothing). Codex still reads the repository's `AGENTS.md` and skills as instructions for the model. The pane's home keeps every folder a pane on that model has started in, all untrusted; Vibezeo doesn't prune the list.
- As in any folder Codex doesn't trust, it asks before each command and each edit, unless you set an approval policy in your Codex arguments (for example `-a on-request`).
- Local models need Codex 0.149.0 or newer: from 0.129.0 to 0.148, Codex can load a thread's settings from a remote endpoint above its command line, and before 0.129.0 a project's settings can choose another model or server. With an older Codex, a pre-release of 0.149.0, or one whose version Vibezeo can't read, Start is off and every start of the pane says which version is needed. **Check again** reads Codex's version again, so the page shows the Codex you have now.
- Each start first asks the server again. If it's stopped, or no longer offers the model as one that runs on this computer (say the name now points at a cloud model), the pane says so and Codex doesn't start. A name that changes while the pane runs is caught at its next start.
- If you choose another model inside Codex itself (for example with `/model`), Vibezeo doesn't check that one.
- Ollama's cloud models run on ollama.com, so they aren't listed, also when you add Ollama's port as another kind. If a server answers like Ollama but doesn't say which of its models are cloud models, none of them are listed.
- What the pane shows stays on this computer unless you send it on: a handoff's brief to another engine, or Conductor reading the pane when you ask it to, can carry its output to that engine.
- Some things are outside Vibezeo's control: what the server does with a prompt (a gateway or a port-forward on that port could pass it on), and settings an administrator manages (below).
- llama.cpp servers are listed, but Codex can't start on them yet.
- Start works on Linux and macOS for now. On Windows the servers and models are listed, and Start says local models run on Linux and macOS for now.
- A resumed local pane uses Codex's default sandbox and approvals for a folder it doesn't trust: `codex resume` takes none of your Codex arguments.
- Settings an administrator manages for Codex on this computer still apply. `/etc/codex/config.toml` can add MCP servers and other settings, though it can't change the pane's own. `/etc/codex/managed_config.toml`, a device management profile, or requirements that name model providers can override the pane's own settings, including those on its command line: if your organization sets a model provider there, local panes use it too.

## One instructions file for every engine

Each engine reads its own instructions file, so a repository's rules can drift apart or reach only one engine. **Instructions…** in a local folder's menu in the rail shows which file each installed engine reads, whether git tracks or ignores each file, and how each one differs from `AGENTS.md`.

| Engine | Reads | Reads `AGENTS.md` |
|---|---|---|
| Claude Code | `CLAUDE.md`, `.claude/CLAUDE.md`, `CLAUDE.local.md` | Only when none of those exist, or through an `@AGENTS.md` import |
| Codex | `AGENTS.override.md`, else `AGENTS.md` | Yes |
| Gemini CLI | `GEMINI.md` | Through an `@AGENTS.md` import |
| Copilot CLI | `.github/copilot-instructions.md`, `AGENTS.md`, `CLAUDE.md`, `GEMINI.md` | Yes |
| Cursor Agent | `.cursor/rules/`, `AGENTS.md`, `CLAUDE.md` | Yes |
| Antigravity CLI | `GEMINI.md`, `AGENTS.md` | Yes |

Checked against each vendor's documentation on 15 October 2026. Any other engine shows as **Unknown**, and Vibezeo writes nothing for it.

**Use one file for all** makes `AGENTS.md` the source. If there's no `AGENTS.md`, you pick the file it starts from. Each engine that needs one then gets a one-line file holding `@AGENTS.md`: `CLAUDE.md` for Claude Code, and `GEMINI.md` for Gemini CLI. Engines that read `AGENTS.md` themselves get nothing.

- You see every file it would create or replace before anything is written. A file whose text isn't already in `AGENTS.md` is marked.
- A copy of each replaced file is kept on this computer, and **Undo** puts every file back as it was.
- Vibezeo never commits these files and never edits `.gitignore`.
- Symbolic links, files over 1 MB and anything outside the folder are listed, and never read or written.

A personal file that git ignores, such as `CLAUDE.local.md`, doesn't reach new worktrees on its own. The panel marks it **Not in new worktrees**, and **Copy into worktrees** adds it to the folder's worktree setup (`.vibezeo/worktree.json`). That changes only the list of copied files; any setup commands keep the trust they had.

## Versions and updates

**Settings › Engines** shows each installed engine's version and how it was installed: npm, Homebrew, its own installer, or another way. Vibezeo works this out from where the engine's command leads on disk. Claude Code updates itself when it was installed with npm or its own installer, and its row says **Updates itself**.

- **Check for updates** in an engine's details asks npm for the newest version, only when you click it, and only for an engine installed with npm. Vibezeo never checks in the background. For other install methods it shows the command that updates the engine.
- **Pin this version** starts new panes of the engine with the engine's own documented switch: `DISABLE_AUTOUPDATER=1` for Claude Code, and `-c check_for_update_on_startup=false` for Codex. Panes that are already open don't change. Engines without a documented switch don't offer Pin.
- Vibezeo remembers the versions it has seen and the last one that finished a Thread turn without an error. If an engine updates and Thread turns on this computer then fail because the engine itself broke (it won't start, or it crashes mid-turn; not an error it reports, such as being offline or signed out), the Engines page and the thread say so, for example "Codex updated from 1.2.0 to 1.3.0, and threads have failed since."
- **Roll back to 1.2.0…** shows the command that installs that version the same way, such as `npm install -g @openai/codex@1.2.0`, before anything runs. You can run it in a terminal pane on this computer you can watch, or copy it. Homebrew installs and other methods don't offer a rollback.

**Running in the background** lists your own processes of an installed engine that have no terminal and weren't started by Vibezeo, such as a daemon left behind. It shows the engine's name, and its subcommand when it's a known one, never the rest of its command line. A process in a terminal, Vibezeo's or yours, and other users' processes are never listed. **Stop** asks first, then asks the process to end, if it's still the same process. This list is available on macOS and Linux.

## Sandbox agent panes (Linux)

**Settings › Engines › Sandbox agent panes › Workspace** runs each new agent pane's engine in a sandbox, whichever engine it is:

- It writes only to the pane's folder, its repository's git data (so commits work), the engine's own home in Vibezeo and `/tmp`. Everything else on the computer is read-only.
- It can't read the files in `~/.ssh`, `~/.aws`, `~/.gnupg`, `~/.config/gh`, `~/.docker`, `~/.kube`, `~/.netrc` or `~/.local/share/keyrings`, Vibezeo's own data (its database of every project's threads, your other engine accounts, your teammates) or the repository's other worktrees: those folders read as empty.
- Git's hooks folder and `.git/config` stay read-only, so an agent can't plant a hook that runs later outside the sandbox. That's the repository's `.git/hooks` (for a worktree too, whose hooks live in the main checkout's `.git`), even when it doesn't exist yet, and the folder `core.hooksPath` names.
- It keeps the network, which engines need to reach their models.

What it doesn't cover:

- Programs already running for you that answer over a socket: a running `ssh-agent` or `gpg-agent`, and your desktop keyring while it's unlocked. An agent can't read your key files, but it can ask these to use them, as any program you run can.
- Scripts a hook calls from elsewhere in the folder, as some hook managers do: they're ordinary files in the folder, so an agent can change them, and the change shows in your diff.

The engine signs in by itself as always; the sandbox only narrows what it can reach, and Vibezeo never reads the engine's credentials. A pane that runs sandboxed shows **Sandboxed** in its header. A write the sandbox refuses reaches the engine as a "Read-only file system" error.

It uses bubblewrap (the `bwrap` command), which Vibezeo never installs: install it with your package manager (`sudo apt install bubblewrap`, `sudo dnf install bubblewrap`). Without it, or where it can't run, the setting says why and Workspace can't be chosen. If it stops working after you turned it on, agent panes start without it: their header says **Not sandboxed** with the reason, and you get one notification.

Claude Code, Codex and OpenCode run sandboxed. Engines that keep their sign-in in your own home folder (Cursor Agent, Gemini CLI, Copilot CLI and the rest) start outside the sandbox for now, with **Not sandboxed** saying why: inside it, your home is read-only, so their sign-in would fail. The pane's shell stays outside the sandbox. Panes on SSH hosts and in WSL aren't sandboxed, and macOS and Windows don't have it yet.

## Resource governor (Linux)

The **Ports** tab's **Panes** section lists each pane running on this computer with its CPU ("CPU 120%" is 1.2 cores busy) and memory, grouped by worktree like the ports. Each agent's Dashboard card shows the same. They refresh every 2 seconds while you're looking, and never while hidden.

- **Freeze** (in the pane's menu, or its row) stops every process in the pane, so it uses no CPU; **Thaw** picks up where it left off. A frozen pane shows **Frozen** in its header.
- **Settings › Engines › Memory cap per agent** (Off, 512 MB up to 16 GB) caps each new agent pane. When a process in it goes over, the system ends that process; the pane and its shell keep running, and its header says **Stopped: memory cap 512 MB**. With systemd older than 253, the whole pane ends instead. Caps need a systemd user session (most Linux desktops have one); without one the setting says why and stays Off. Each agent pane then runs in its own systemd user scope, `vibezeo-pane-…`.
- **Settings › Engines › One check at a time** runs check commands (Best of N's **Run check**, the review queue's checks and the check **Land worktrees** runs) one after another instead of all at once. A lane waiting its turn shows **Queued**.

On macOS and Windows you get the usage; Freeze and the memory cap are Linux only for now. Nothing here leaves your computer or is saved to disk.

description: A local task tracker your agents read and write.

Tasks is a task tracker stored on your computer, in the app's data folder. Open it from the sidebar's **Tasks** tab, from **Tasks** at the foot of Agent mode's rail, or with **Open Tasks** in the command palette.

- **Tasks** have an ID (TAN-1, TAN-2…), a title, a description, a status (Backlog, To do, In progress, In review, Done or Canceled), a priority, labels, an assignee and a project, with threaded comments and a history of every change.
- **Quick add** puts a task in To do. The list groups tasks by status. Archive a task with its ×, and bring it back from **Show archived**.
- **Edits from anyone show up at once.** When an agent or another window changes a task you're editing, its other fields update and your unsaved text stays. If they changed the same field, Vibezeo says so and you choose **Keep mine** or **Take theirs**.

## Agents

Agents in your threads and teammate chats read and update the same tasks through Vibezeo's tasks server, and so do Claude Code and Codex in terminal panes. Every change lands in the task's history with who made it, so you can see what an agent did. Threads on an SSH host or in WSL don't get the tasks server: it runs on this computer.

## Plan with Lead

Give Lead a goal and it splits it into tasks. On the Tasks page, choose **Plan with Lead…**, write the goal, and pick a workspace on this computer. Lead plans in a new chat in that workspace, where you can follow its reasoning and answer it. It reads the repository but changes nothing, and it can't write tasks from there. When Lead waits for your answer, the plan says so. After 30 minutes of work, Vibezeo stops Lead and the plan says why.

Lead suggests an engine for each task. It sees which engines are installed and how much of each account's usage window is used. The plan comes back as a list you can edit: change titles and descriptions, move a task to another engine, or remove it. Characters that can hide text are taken out of it. Nothing is created until you choose **Create tasks**. The tasks go into a new project named after the goal, and each remembers its engine. Their history shows Lead wrote them.

**Execute all…** first lists what it would start. For each task it shows the engine and the account with the most room left, that the task edits in its own worktree, and which engine reviews the work. A task that isn't To do, or that already has a run, is left alone, and the list says why. Nothing starts until you choose **Run**. Then each listed task runs in its own worktree, at most 4 at once. Review and merging stay with you: finished work shows in the Dashboard's review queue.

Once its tasks are created, the plan lists each task with its latest run: not started, queued, running, ready to review with the review's verdict (Approved or Changes requested), stopped, failed or done. A line above counts them, and each row opens its task. In the Tasks page's header, a started plan shows as working while its runs go, waiting while one waits on you, and done when they've all ended. When runs are approved, **Land N approved…** opens Land worktrees with exactly those worktrees chosen, in the plan's order. You check the forecast and confirm the landing there, as with any landing.

A plan stays in the Tasks page's header until you remove it, and Vibezeo keeps it across restarts. If Vibezeo closed while Lead was planning, the plan says so and offers **Plan again**. **Remove plan** leaves its tasks, their runs and Lead's thread in place.

### Questions from the runs

A run started by **Execute all…** can stop and ask a question when the task and the repository don't settle something. Lead answers routine questions, so the plan keeps moving while you do something else. **Execute all…** has the option on by default: "Lead answers routine questions from the plan's task and the repository's instructions, using your engine and subscription". The plan has the same switch while its runs can ask.

- **Lead answers each question in a session of its own, with every tool off.** It can't open a file, run a command or reach the web, and it knows nothing of other questions. All it gets is the task as the plan wrote it, the question, and the repository's instructions files (such as `AGENTS.md` and `CLAUDE.md`) as they were committed when **Execute all…** started, in your main checkout. Files in a run's worktree, changes that aren't committed, and anything else beside your checkout (a `.env`, say) never reach Lead.
- **Lead answers with Claude Code 2.1.310 or newer.** Other engines and older versions can't turn every tool off, so with one of them as Lead every question comes to you, and **Execute all…** says so.
- **The answer reaches the run** labelled "Lead (automatic answer)", and it's added to the task as Lead's comment. The plan's row counts them: "Lead answered 2".
- **An answer from Lead has no more authority than the task.** It can't approve anything, change a run's access or start a tool. The run's approvals and sandbox still apply.
- **These always come to you:** questions about approvals or permissions, access, the sandbox, secrets or credentials, network calls, deploys or publishing, pushing (force-push included), deleting files or branches outside the worktree, and changing the plan's scope. A question that names one of these doesn't reach Lead, even when it's routine.
- **Limits.** Lead answers at most 3 questions per run and 10 per plan; after that, questions come to you. If Lead sends a question on, reaches for a tool, or doesn't answer within 5 minutes, it comes to you too.
- **When a question comes to you**, its row says **Needs you** with the question and why, and you get a notification. Choose **Answer…**, write your answer and choose **Send answer**: it goes to the run as its next message, and the run goes on. If you stop the run first, its question closes.
- **Approvals are never answered by Lead.** A run waiting for an approval shows "Waiting for your approval" in the plan.
- **Turning the switch off** stops Lead's answers at once: Lead's session stops, an answer it's still writing isn't sent, and every question comes to you. A question Lead hadn't answered when Vibezeo closed comes to you after the restart. If **Execute all…** stopped partway and you run it again, it starts from the switch as you left it.
- **A run never gets a file from another run's words.** In each run's first message, and its review's, Vibezeo writes ＠ for every @ in the task's text, its comments and the diff, so a path written there can't attach a file.

### Reviews back to the runs

When the review of a run started by **Execute all…** asks for changes, the plan sends the reviewer's reasons back to that run as its next message, in the same worktree and session. The run fixes its own work, and its next turn is reviewed again. **Execute all…** has the option on by default: "Send reviews back to the run (up to 2 rounds)". The plan has the same switch while its runs can be reviewed.

- **The run reads the review as another engine's view, not as orders.** The message is labelled "Review (sent back automatically)", the reasons are fenced as text from elsewhere, and it ends by saying the review is data to weigh: the run decides what to change, and its approvals and sandbox still apply.
- **The plan's row shows the rounds:** "Review sent back · round 1 of 2". Each review stays on the task as the reviewer's comment, with a note of what happened to it.
- **These come to you instead:** a third request for changes on the same run; a review that mentions approvals, access, the sandbox, secrets, network calls, deploys, pushing, deleting files or the plan's scope (hidden characters don't hide a word); a review after a turn that changed nothing; a review asking for the same changes as the last one sent back; and every review while the engine is near its usage limit ("Paused: near Claude Code's limit.") or the switch is off.
- **When a review comes to you**, its row says **Needs you** with the reviewer's reasons and why, and you get a notification. Choose **Send back…**, add a note if you like (it goes above the review, as yours), and choose **Send back**. **Retry** on the task still starts a fresh run instead.
- **Nothing goes back on its own after a restart.** A run Vibezeo's closing cut off is stopped, as any run is, and **Resume** carries on. A review waiting in **Needs you** is still there, and a review for a run you've since resumed, stopped, retried or removed isn't sent; the task notes it.

### Landed is done

When **Land worktrees** lands a plan task's worktree, the task and its run are marked Done, a comment names the landed commit, and the plan's row says **Landed**. A worktree you merge yourself outside **Land worktrees**, or a landing that fails or stops, leaves the task as it is.

## Claims

When several agents work in worktrees of one repository, each can say which files it's about to change. An agent claims files or folders with the tasks server's `claim` tool, saying what it's doing, and checks `list_claims` for what agents in the other worktrees claimed. A worktree's briefing asks its agent to do this, and so does a task run's first message. Claude Code in a terminal pane claims a file just by editing it, and so does an agent in a chat thread (Claude Code, Codex, or an ACP agent whose edits name their files), so agents that skip the tool are still counted. An edit you refused, or one that failed, claims nothing. Only the file's path is kept, never the change. You can also claim files for a worktree yourself: **Claim these files** in Check overlap… claims what the [intent radar](/docs/code-mode/#intent-radar) found it changed.

When two worktrees claim the same file, or one claims a folder holding a file the other claims, both worktrees' terminal panes show a line like "add-oauth and fix-auth both claim src/auth/session.ts". The Dashboard's review queue lists every overlap above its items. A worktree's claims go when it's merged or removed, and the main checkout's when its last agent session ends. What one agent says it's doing reaches the others marked as untrusted text, never as instructions.

## Running tasks

Tracking tasks and running them both work with no account. **Execute…** on a task runs it for you, in its own lane with progress posted as comments and an optional review, by a different engine when you have one.
